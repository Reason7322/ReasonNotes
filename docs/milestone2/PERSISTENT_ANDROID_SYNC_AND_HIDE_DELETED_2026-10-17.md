# Android sync confirmation across long offline intervals and live-only note picker

## Original observable goal and full acceptance
ReasonNotes must remain a responsive, reliable Fedora/Android app with intact user notes and immutable histories, secure receipt-backed KDE Connect sync, no fake delivery confirmations, F5 desktop receive, and permanent cross-device deletions while both apps are open. The user specifically reported Android's two-minute "computer confirmation not received" timeout and asked what happens if Fedora ReasonNotes is only opened five hours later. The requested outcome is durable, non-expiring pending confirmation across Android activity/app closure; when a real receipt arrives hours later, Android validates it and can display confirmed status the next time it checks. Deleted notes, including historical tombstone revisions, must not appear in "Choose notes" or be selectable/sent through normal manual outgoing sync.

## Implemented
- Removed the two-minute confirmation deadline entirely. The Sync activity checks while foreground (now with a 15-second poll interval), stops checks on pause/destroy, never sends a retry just to get status, and never flags lack of confirmation after an arbitrary time as an error.
- Added a one-field, versioned SyncConfirmationRecord to preserve the revision IDs and exact selection of the last newly requested send in a small private Android preference. The actual delivery ledger and canonical receipt validation remain the only source of delivery truth; the preference is not a confirmation.
- On cold launch and on Android Settings -> Sync reopening, load the saved revision IDs, inspect and scan incoming receipts, and show success only after all tracked revisions have persisted confirmed receipts. The existing MainActivity foreground receiver may import receipts while SyncActivity is closed. No always-on background process or requirement to leave Android open.
- Invalid or corrupt stored metadata is ignored safely; no receipt or note data is erased, reset or forged. A new transfer request supersedes the last UI checkpoint, but a no-op sync does not destroy the previous request's pending status.
- In SyncPlanner catalogue, exclude deleted-head notes regardless of delivery state (including pending and needs attention); in normal Sync all and Sync selected outgoing plans, exclude all revisions from entirely deleted notes, even with explicit bounded retry. Keep legacy tombstone bytes and their ledgers unchanged, keep forced internal repair path separate, preserve outstanding receipts, and do not alter the independent foreground permanent-purge propagation.
- SelectionModel filters deleted notes even if a caller passes stale catalogue data, refuses programmatic checkmark selection for a deleted ID, and strips removed IDs from restored selections.

## Validation / remaining checks
- Android testDebugUnitTest assembleDebug: 152/152 passing. Updated 4 prior tests that required selectable tombstones. Added tests covering deleted entries and picker selection, cold-restart persisted record across arbitrarily long delays, malformed persistence, live-only outgoing behavior, and no resurrection.
- Fedora release, sources, and app data are intentionally unchanged.
- Before user-visible completion: commit, verify SHA and signing, back up before in-place Android install, compare all private user files byte-for-byte, launch app, verify picker no longer offers the specific two legacy deleted notes from screenshot, check no notes/history changed, and verify no request or UI test creates a bogus confirmation. A full five-hour live wait is not required to establish lack of a code deadline, but a future delayed real receipt remains a useful user acceptance test.
