# Android ReasonNotes incoming-scan latency and obsolete receipt correction

## Full original product acceptance
The user wants the Android note app to display desktop-transferred new notes promptly without a minute-long delay, while maintaining responsive mobile UI, reliable KDE Connect sync in both directions, manual F5 desktop receive behavior, instant permanent cross-device deletion while both apps are open, and complete preservation of all existing unpurged notes/history. The app must not falsely confirm deliveries, resurrect deleted notes, reset sync state, clear receipts/exchange files, or perform unsolicited transfers. The desktop is feature-complete; this change is Android-only. The broader Android polish work remains open.

## Actual device evidence before modification
- Fedora had requested two new revisions from the same note to the phone, each with one KDE Connect request, no confirmed acknowledgment in desktop ledger.
- Once POCO X6 5G was connected via authorized USB ADB, both revision IDs were found in the Android private history and in the public ReasonNotes Exchange folder. The revisions eventually arrived and were imported; there was no need to recreate the note.
- 147 files in public exchange, 145 Markdown files including old receipts. Android private history 126 immutable revision files; receipt inbox 89 entries. Do not infer historical deletion from these counts; the user's past deletion operations had changed counts legitimately.
- The specific displayed receipt error e502d31e...receipt.md: receipt names an unknown revision refers to a cryptographically valid receipt for a note whose permanent-purge marker exists in the phone repository; the historical revision was intentionally erased. The stale receipt is not a failed new-note import and can never be accepted as delivery confirmation.
- Source showed DocumentFile.listFiles followed by per-item DocumentFile.getName/isFile queries, repeated full repository revision reloads for receipt validation, duplicate revision ledger/receipt scans, and the home screen updating only after the entire scan completed. These are plausible latency sources, but no actual baseline phone scan latency was instrumented in the old build; KDE transfer time also remains a possible contributor.

## Implemented (Android only)
- Use one Android DocumentsContract content-resolver child query to obtain names, document URIs and modification timestamps in a batch. The incoming files remain in SAF; no provider permissions/data are changed. Process revisions first (latest first) and receipts after. Files are still opened, canonical bytes checked and validated; neither filename nor timestamp authorizes imports or confirmations.
- Reuse a single local revision snapshot for strict incoming receipt validation. Keep the live permanent-purge marker check so snapshot data cannot override a concurrent deletion. Retain wrong-peer, never-requested, mismatched note/revision and signature rejection.
- Reuse durable reasonnotes-imported event and queued-receipt state to avoid rerecording the same already-validated import evidence on every scan. History bytes are still verified against immutable local contents before treating duplicates as recorded.
- On each newly completed durable revision import and acknowledgment queue operation, notify the main thread to refresh the visible home list before unrelated old receipts finish scanning. This does not start outgoing transfers or run a background service while app is closed.
- Cryptographically validate receipts, then ignore only receipts addressed to this device for notes proven permanently purged, both in the public exchange scan and local receipt-inbox recovery. Preserve the receipt files as received (except existing purge process which already retires receipt state), preserve deletion markers, never confirm the old revision and never resurrect content. Unknown or wrong-destination receipts for unpurged notes remain errors.
- If new notes arrived alongside a genuinely bad receipt, show the import result and preserve the warning instead of replacing the success with the first error. Add a compact logcat performance line with files/imports/replays/errors and wall-clock milliseconds; never log note content, private keys or paths.

## Validation and remaining acceptance
- Offline Android testDebugUnitTest assembleDebug: 139/139 passed. New tests cover obsolete purged receipt vs valid unknown, wrong destination, malformed file, repository recovery after stale receipt resurfaces, strict snapshot receipt/peer validation, redundant receipt idempotency, deletion-fence race safety, and combined import+warning status.
- Fedora source, installed launcher and note history unchanged.
- Critical remaining task: approved in-place Android installation after full private app-data backup and exact post-install checksum comparison. Real POCO SAF provider performance, visible note appearance latency, receipt warning disappearance and real home UI must be measured on device after upgrade. A JVM benchmark is not equivalent to a physical-device measurement. Any unexpected errors warrant stopping rather than resetting history or exchange.
- If device does not support expected SAF query columns, treat failure as error; do not silently drop incoming revisions or claim success.

## Physical device checkpoint after first installed patch
- SHA 02d7328 installed in-place on connected POCO X6 5G with matching signing certificate. A 304-file private app-data backup was verified, and post-install private app files were byte-for-byte identical before launch. This first patch had 139/139 Android tests.
- First observed actual device scan: files=145, imported=0, duplicates=43, receipt replays=43, receiptsRejected=0, msTotal=27793, msFiles=15242. The earlier deleted-note receipt no longer causes the visible warning. This was a duplicate-only scan after the desktop revisions had already been imported, not a live incoming-note latency benchmark.
- The scan still took 27.8 seconds, which is unacceptable. Additional code inspection found that receipt-inbox recovery for approximately 89 existing receipts repeatedly rereads the full delivery ledger and event log for already-confirmed receipt records.
- Second patch: recovery caches validated peer-ledger and audit-event snapshots during one scan, skipping repeat disk reads/writes for confirmations already durably recorded, while still parsing receipts, validating the note/revision/peer and verifying that permanent purges remain authoritative. Reconciliation of missing audit records and genuinely new receipts is retained.
- Physical timing after the second patch has not yet been measured; the acceptance milestone remains INCOMPLETE until this is verified.
